## 1. HEADLINE — SM8250 boot chain: GRUB → ROCKNIX ABL (`ad843ff62b`, PR #3127, merged 09-03)

`devices/SM8250/options`: `BOOTLOADER="arm-efi"` → `"qcom-abl"`. Tested upstream on an RP
Mini V2, fresh flash and from "stock abl / stable grub ROCKNIX build" (i.e. booted on
`/KERNEL`). Mechanics, read from source:

- **KERNEL format** (`packages/linux/package.mk` `makeinstall_target`, qcom-abl branch):
  `gzip(Image)` + **every** built `*.dtb` concatenated, dummy ramdisk, `mkbootimg.py
  --header_version 0 --cmdline "boot=LABEL=… disk=LABEL=… ${EXTRA_CMDLINE}"`. The ABL
  picks the DTB out of the appended set. No `/boot/grub/*.dtb` is installed any more.
- **`update.sh` now does two new things on every in-place update:**
  1. runs `/usr/bin/updateabl`, which reads `abl_a` and `abl_b` on internal UFS, and if
     either sha differs from the shipped `abl_signed-SM8250.elf`, **`dd`s the ELF onto BOTH
     slots** (no untouched slot left as fallback). `rocknix-abl` is v1.1.9 at HEAD
     (bumped today, `e9ff9dbd11`).
  2. `rm -rf /flash/boot /flash/EFI` — GRUB, both grub.cfg twins, grubenv, and the DTB
     dir are deleted.
- **FALSIFIES** `UPSTREAM_20260901.md` §Boot path: *"the in-place update never flashes the
  ABL partition."* True for 20260901; false for SM8250 from the first qcom-abl build on.
  (The abl_dev counter that section describes was since replaced by a numeric default —
  etk `f67ebb5`.)
- **The ABL source is not public** (`ROCKNIX/LinuxLoader` → 404; `ROCKNIX/abl` only wraps
  the release). Which file it boots, what it does with a non-boot.img, and whether the
  v1.1.8 "allow grub selection from abl" survives v1.1.9's "simplify boot process" are
  **unverifiable from source** — only from release notes or hardware. Working inference:
  it loads `KERNEL` from the boot FAT (that is the only kernel the qcom-abl image ships,
  `scripts/mkimage` → `::/${KERNEL_NAME}`).

### 1a. THE SLOT TRAP — an ETK-specific no-boot path (applies to public v0.9.0 users)

The initramfs writes the update's kernel to `/flash/${IMAGE_KERNEL}`, where
`IMAGE_KERNEL` = the `BOOT_IMAGE=` GRUB put on the cmdline (`busybox/scripts/init`
L1170–1173, L1125). That is the documented 20260901 "updater trap". Under qcom-abl it
compounds:

1. Rig in `KERNEL_DEPLOY_MODE=default` (the install default) boots `etk-gtk-test` →
   `BOOT_IMAGE=/KERNEL.gtktest`. (The `etk-fallback-stock` entry is no better: it
   boots `/KERNEL.etk-stock`.)
2. October update: new stock **boot.img** → `/flash/KERNEL.gtktest`. `/flash/KERNEL` keeps
   the old 20260901 **raw Image**. `updateabl` flashes the ABL; GRUB is deleted.
3. Next boot: the ABL has no GRUB to hand off to, and `/flash/KERNEL` is not a boot image.
   **Expected: ROCKNIX does not come up** until `KERNEL` is replaced by hand (card in a PC:
   the new boot.img is sitting in `KERNEL.gtktest`). ABL failure behaviour unverified.

Upstream's migration test never exercised this — their rigs boot `/KERNEL`.

**Candidate guard (UNVALIDATED — mother-repo change, harness + cold boot first):** append
`BOOT_IMAGE=/KERNEL` to the END of ETK's GTK grub `linux` lines. The init loop is
last-wins, and `IMAGE_KERNEL` is used for nothing but the update target (L1015–1125), so
updates would land in `/flash/KERNEL` — exactly where the ABL looks. It also changes the
GRUB-era updater-trap dynamics osguard Phase A was written for; the harness must cover both.
If this ships, it must reach public rigs **before** they take ROCKNIX 20261001.

### 1c. Kernel-lane consequences (this repo)

- `build_72.sh` builds `Image modules` only (L117). ABL era needs: `dtbs` from the staged
  device DTS, gzip + append, `mkbootimg` (header v0) in the container, and the ETK cmdline

## 2. SAFETY — pm8150b charger float voltage (open PR #3382; affects our CERTIFIED kernel)

`0011-qcom-pm8150b-charger.patch` programs `FLOAT_VOLTAGE_CFG` with the **PMI8998** scale:
`(voltage_max_design_uv - 3487500) / 7500 + 1`. For the Retroid battery node
(`voltage-max-design-microvolt = 4400000`, common dtsi) that writes **0x7a**, which on the
**PM8150B** scale (3.6 V + 10 mV/step) is **4.82 V** for a 4.40 V cell. The driver never
writes `FAST_CHARGE_CURRENT_CFG`, which the #3382 author read as 0x6b = **5.35 A**.

- Present in **every** SM8250 build since the 2025-07-13 import (only the capacity math
  was touched since, `0393a000d2`) — **including `20260901-0.5`**. Driver is
  `CONFIG_CHARGER_QCOM_SMB5=y` (built-in; its Kconfig help still says "PMI8998"), so it
  lives in the kernel image **we** ship, and the fix is module-ABI-safe for us to carry.
- Measured by the PR author on an **RP5** (0x1070: 0x7a → 0x50, 0x1061: 0x6b → 0x26 after
  fix). **CONFIRMED ON OUR FLIP 2 (2026-09-26, operator-run, read-only):** regmap
  debugfs `0-02` → `1061: 6b`, `1070: 7a` — byte-identical. Same session, at rest on a
  5 V (non-PD) charger: `battery` status Full (the driver reports Full only on the PMIC's
  hardware TERMINATE_CHARGE), `voltage_now` 4,279,530 µV, capacity 100. The cell at rest
  is below its rating, but that does NOT clear the setting — post-termination relaxation or
  a pack-protection cutoff/release would read the same; the pack's protection IC is the
  backstop we have been leaning on. On 5 V input the 5.35 A setting is input-limited.
- **CARRIED as ETK patch #9** (`patches-7.2/0009-pm8150b-charger-float-voltage.patch`,
  PR 0018 verbatim, static-verified; PATCHES.md #9). `0019` (restore USBIN after VBUS
  source) applies stacked but is a separate bug — not carried. `build_72.sh` now
  fingerprints the staged patch set (the old bare stamp would have silently skipped #9 on
  a remint — sandbox-reproduced) and VERIFY fails the lane if the fix is absent.
  Acceptance: cold boot on the minted kernel → read-back `1061: 26` / `1070: 50`.
  **MET 2026-09-26** — `20260901-0.5.1` (sha `3cd2a297…`) is live on the rig with
  `1061: 26` / `1070: 50` (VALIDATION.md). Public v0.9.0 users still run 0.5: shipping
  0.5.1 to them is a publish (operator), best bundled with the §1a guard before Oct 1.

## 3. Type-C / DP — the "redriver" is a phantom (`e4461cfea5`, merged 09-21)

Upstream: the `nb7vpq904m` node was a verbatim copy of `qrb5165-rb5.dts`; **nothing
answers at i2c15 0x1c**; the driver never reads `CHIP_VERSION_REG` and discards every
`regmap_write` return, so it binds to an absent chip and reports success. The SBU/AUX pair
is a **GPIO analog mux on tlmm 8 (select) / 9 (enable, active-low)** — tlmm 9 was the pin
the phantom claimed. Fix: drop the retimer, connector straight to the QMP PHY,
`gpio-sbu-mux` on the SBU port. Measured on RP5 + official dock, both orientations: USB 3,
PD, DP 1080p60 (pin assignment D, 2 lanes). Flip 2: **dtb compile-tested only**.

**This is corroborated by our own evidence and very likely closes the parked
ReverseOrientationFix.** Our 2026-08-10 Android golden-reference probe (VALIDATION.md
§Reverse-orientation, session-2 addendum) found Android keeps the redriver's i2c bus
disabled and "ROCKNIX's DTS invents `tlmm 9`"; DBG9 (gpio9 hands-off) was the untested
cell. **Falsified in our ladder:** `.11`'s "redriver told correctly (AUX_CC=0x1 written) —
module/mux stack fully exonerated" — those writes went to no chip; the narration logged
intent, not effect. The "AUX_CC cross position does not conduct on this board" theory is
superseded: there is no crossbar; the real mux was never driven.
